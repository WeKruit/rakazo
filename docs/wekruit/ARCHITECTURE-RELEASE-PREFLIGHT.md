## E3: restore the correct backup format into an approved empty target

A valid archive is not proof of application/database point-in-time consistency.

After those decisions, the operator should:

2. Confirm the destination is empty, isolated and cannot dispatch jobs, models, messages or webhooks. Record its identity out of band; reject the production target. For the custom format use `pg_restore --exit-on-error --single-transaction --no-owner --no-privileges --dbname=<approved-empty-target> <approved-dump>`; the omissions require explicit post-restore role/grant verification and are not a privilege policy.

## E4: reuse the existing ordered fallback chain

The code already has ordered backup models scoped by **user and Space**, read in `executor.ts` from `spaceBackupModel`; this is broader than a per-bot setting. The primary model can remain bot-selected. Use existing `models/backups` settings and connected credentials, not a new router. Before changing the list, identify every bot in the test user/Space that would be affected. Keep the exercise in an approved isolated user/Space and snapshot its existing primary/backup choices.

Existing `pi-runtime.ts` fallback selects a compatible, independently authorized backup on a retryable provider error **before partial text/tool output**. It skips missing credentials, duplicates and incompatible context/capability choices; it does not borrow primary or process credentials. Ordinary400/401/403, revoked credentials, permission refusal and cancellation deliberately do not trigger fallback. A narrow provider-specific usage-limit403 exception exists; do not generalize it. Once output/tool activity starts, blind replay could duplicate effects and is not the failover contract.

Minimal publisher drill, after connection-change and bounded provider-call authorization:

1. Verify a genuinely independent existing backup connection for the test user/Space, tool/image/context compatibility and quota. Save ordered choices through the existing settings and retain a rollback copy privately. No new paid service or credential is implied.
2. Run one baseline synthetic conversation without external-effect tools and record primary completion. Induce a separately authorized test-primary503,429 or connection timeout **before output** (or a controlled provider outage on that test-only connection). Never revoke a shared production key or disable a global provider.
3. Confirm the same run switches to the intended backup, completes exactly once, retains context, records provider/usage accounting, and produces no duplicated tool effect. Retain run/provider identifiers privately and latency/error evidence, without credentials or actual recruiting data.
4. Run negative controls: missing backup credential, ordinary401/403, partial tool output, and user cancellation must retain the existing safe failure behavior. Restore original test connection order and confirm a fresh primary baseline.

If “stop the primary connection” means deleting/revoking its key, that conflicts with the existing nonretryable authentication boundary. Decide on an outage simulation rather than changing that safety rule. No real primary connection was disabled and no live backup completed a conversation here.
