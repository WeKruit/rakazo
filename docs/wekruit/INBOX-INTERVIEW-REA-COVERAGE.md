## Explicit data and capability boundaries

- **Unread is exact for the indexed stored corpus, with explicitly partial provider coverage.** The additive message projection retains original email DTOs, artifact references, import receipts/corrections and exact source/organization/campaign/mailbox/message identities. The existing background loop populates it from durable native receipts, imports and CRM mirrors; it does not poll providers or claim all provider mail is synchronized. Navigation labels its count as unread in saved mail with partial coverage; unknown threads are reported separately, and failed reads remain unavailable. Sent mail never adds unread. Personal cursor changes invalidate the same account's navigation count. Database comparisons explicitly use UTC even when the session timezone differs.
- Finite import/CRM backfill coverage describes the qualifying owned records examined as of the last completed background pass (`checkedAt`), not the current display-read snapshot. It does not mean provider freshness or historic native completeness. A newly saved receipt or mirror correction is picked up on the next existing background check; original data and full artifacts remain untouched.
- Candidate summary fields are shown only when the already-loaded, authorized data establishes the exact person. Server pages reuse exact saved role candidate rows, current Reviewer provenance and owned saved profiles. CRM mirrors join exact owner/source/organization/candidate contacts. A person without retained profile/material data does not acquire invented facts or a fabricated grade.
- The current saved-plan availability contract binds native Cal availability and `create_booking`. A Cal event type owns location; guest additions are separate native operations. Google Calendar's existing native event operations remain available to the authorized agent, but they are not represented as Cal slot proofs or silently converted into this saved-plan contract.
- Editable arbitrary date/time ranges and a claim that all calendar conflicts were excluded would exceed the recorded availability evidence. The UI chooses actual observed intervals and asks the existing role assistant to check availability when none exist. A fresh availability check and explicit native approval still precede any real booking/send.
- Material availability and resume facts are not interchangeable with confirmed interviews, interest or Reviewer grades. No source field means unknown, not false or a derived positive claim.

## Additional stored-mail checks

`packages/db/src/recruiting-global-inbox.postgres.test.ts` uses a dedicated local PostgreSQL database: complete body and attachment retention after snippets (including searchable retained words), distinct sources, owner/space isolation and authorization rollback, 501-message bounded backfill with later import corrections, keyset pages, personal unread baselines and sent-only exclusion. `actor-db.postgres.test.ts` exercises restricted-role isolation and both explicit and conditional policy installation for the projection. Eleven PostgreSQL checks include outbound-only search text finding its incoming conversation card, latest attachment descriptor corrections and out-of-order original attachment retention, exact saved profile/current Reviewer mapping and refresh after new grades or role revisions, separate organization identities and a real second-role personal cursor alias. Additional local coverage exercises 24,000 imported messages to completion without display reads, immediately available cursors during partial indexing, read-only list/summary reads and absence of background-created personal baselines. Summary reads skip role catalogs, candidate/profile lookup and body/attachment projection. Local database proof and synthetic App screenshots remain separate from production/provider acceptance.


A local PostgreSQL 16 measurement over 24,000 synthetic indexed messages (three runs after one warmup, no wall-clock test threshold) recorded page-30 reads at **1064.9 / 1076.5 / 1064.6 ms** and summary-only reads at **224.3 / 215.9 / 256.3 ms**. This measures the local implementation, not deployed latency. The temporary benchmark runner was removed; captured values remain in `/tmp/rakazo-inbox-24k-read-benchmark.json` for review.

Offline native replay uses the configured CRM endpoint solely to validate retained native provenance, never to call a provider. Captured history is normalized once per role. Generic retained tool receipts use bounded keyset batches and exact receipt observation timestamps; each normalized batch is written in chunks without reparsing every mail offset. The existing background timer runs for import/native-only owners even without a configured CRM endpoint. Personal read initialization remains separate.
