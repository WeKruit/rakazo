# AGENTS.md

## WeKruit design principles

Build a recruiting multi-agent product by composing Rakazo's existing harness with the people-search agent. These principles govern implementation choices in the WeKruit plans; historical task lists and existing custom code are not authorization to expand another agent platform.

1. **Reuse the harness.** Rakazo's frontend/backend and native Pi runtime own crew chat, delegation, sessions/history, memory, skills, MCP, questions, approvals, files and recovery. Trace and use the existing capability before changing it. Do not build a second harness, orchestrator, provider router or parallel interaction layer.
2. **Treat the search as an agent.** The people-search agent owns finding and checking people, and Reviewer grades them. Do not rebuild these decisions or independently reassess, rank or qualify candidates elsewhere. Autumn is retired: do not route search, scale-out or grading to it.
3. **Compose agents, not a fixed recruiting pipeline.** Main understands the user and coordinates; Sourcer runs the scale-out: forward JD/playbook context, translate human feedback into the next wave of the same search, store actual outputs, and relay concise results/questions. The formal playbook calibration presents exactly ten profiles; subsequent feedback may target any subset of people or a general search direction. Do not require ratings for every person before accepting feedback or expand a targeted correction into mandatory reassessment of the entire pool. Use native group chat, delegation and handoffs. Additional specialists must serve a real product need and reuse these same mechanisms.
4. **Put recruiting behavior in instructions and skills.** Stable responsibilities belong in bot instructions; playbook guidance belongs in existing skills. Agents decide relevant next steps from context. Do not translate the playbook into a custom rules engine, business DSL, fixed questionnaire or mandatory series of domain-tool calls. Preserve actual human decisions and approval requirements.
5. **Keep the product layer small.** Build the requested chat, evidence/results, feedback and Dashboard using existing components. Persistence serves actual results, source references, identity/deduplication and task/session links. Define an output schema only when an actual return/storage/display need requires it; a schema must not become the agent's reasoning engine or require users to fill technical fields. Recruiter-facing conversations use role/candidate names, business progress, evidence and decisions. Internal task/artifact/shard IDs, tool names and request JSON belong in explicitly enabled deployment-owner diagnostics. Agents resolve internal continuity themselves; native questions provide direct answer inputs. Preserve exact real consent targets, recipients, content and scope.
6. **Preserve autonomous continuity.** Feedback becomes a clear follow-up on the same search. Keep the original native thread, session and question/approval card through answers and recovery. Ordinary searches and continuations use existing authorization, quota and rate limits without per-call approval. Internal execution is autonomous: candidate storage, deduplication, role association, CRM record updates, drafts, memory updates and agent delegation do not require approval by default. Require the user's exact decision before sending outreach or external interview invitations, including the recipient, content and time. Clarifying a material missing/conflicting requirement or receiving candidate feedback is ordinary conversation, not permission to read or save data. Reuse native policy and execution receipts; do not implement autonomy by fabricating approvals or globally disabling authorization. Preserve separately configured explicit user approval rules, account isolation and budget boundaries.
7. **Replace providers through existing boundaries.** Use native per-bot model/connection and memory/skills/MCP settings for supported substitutions. Do not create a new framework merely to promise future runtime or plugin interchangeability.
8. **Prove the user workflow.** Verify normal chat → native Main/Sourcer collaboration → search results/evidence → user feedback → same-task continuation using actual recruiting work and the connected people search. Product acceptance must exercise real roles, returned candidates, sources and decisions; do not create more demonstration conversations or substitute fabricated results for this evidence. Focused deterministic code checks remain implementation checks, never business acceptance. Develop independent UI, agent and native automation work in parallel. Explain any demonstrated native gap before making the smallest integration change. Preserve existing work and records; do not expand or blindly remove custom layers simply because they exist.
9. **Make business capabilities agent-callable through existing tools.** Candidate persistence, scoped feedback, CRM changes, hold/pass decisions, correspondence and interview scheduling must be available to the authorized agent through the existing `ConnectorTool`/`ToolHost` and native executor. Reuse assigned service MCPs and existing connectors first; when an operation is missing, adapt the existing business service through that same boundary. Do not create one MCP server per feature, another tool router, or a separate implementation of the operation for chat. Web controls and agent tools share authorized business services and persisted records; the UI need not invoke an LLM or MCP to perform its action. Instructions and skills define goals, completion checks and specialist handoffs; native execution enforces account scope, approvals, receipts, duplicate protection, pauses and recovery. Recording a hold/pass decision and sending a rejection message are separate operations with separate authority.
10. **Apply the existing tool-chain and cost research.** Reuse native tool discovery, per-bot assignments, deterministic tool schemas, skill loading and Pi compaction. Keep complete provider output in existing durable storage; pass bounded summaries, exact saved references, cursors and scoped changes through agent context. Read only the passages needed for the next action instead of copying entire candidate pools between agents. Reuse paid results and verified receipts; never cache authorization, a human approval or mutable business state as though it were current. Measure complete successful-task usage, including specialists, retries, compaction and external calls. Add a retrieval or compression dependency only after an observed gap remains and its quality/cost effect is measured.

Recruiter-facing confirmations describe the actual business decision. G0/G1/G2 and the other playbook gate codes are internal identifiers, not questions or button labels. Read the supplied JD and saved answers first, present the known requirements or exact material being approved, then ask only the consequential unresolved decision in ordinary language with concrete choices and a custom answer. Do not ask a recruiter to "confirm G0", repeat information already supplied, or turn a future reply policy and optional material into a generic mandatory questionnaire. Keep genuine business approvals and the playbook order intact; wording changes do not approve or replace an existing waiting card.

Reuse the user's existing service integrations before requesting another provider. Instantly correspondence, Gmail correspondence and calendar operations are separate capabilities to verify against actual connections and tools. A connector platform such as Composio is an optional access mechanism, not a recruiting prerequisite or evidence that the source product uses it. Do not block authorized sourcing on configuring an unrelated mail/calendar connector, or assume that a source-product OAuth login or standing-send rule transfers to this product.

The current priority is complete playbook acceptance for both real roles. The human has explicitly restored v1.0's order: S1/S2 preparation and actual G0/G1 decisions, S3 exactly ten calibration profiles, S4 feedback and explicit human G2 approval, then S5 scale. Do not retain the earlier pool-first override. Ten is the calibration review size, not a storage cap: preserve and display all already-returned candidates and reuse saved findings instead of repeating paid research. Existing pools are not retroactive G2 approval. Feedback may address any person, subset or general direction; the search and Reviewer own matching and revisions. Do not invent approvals or automatically approve calibration, imports, outreach or scheduling. Reuse the native harness and tool boundary rather than adding a local evaluator, fixed workflow engine or new infrastructure.

Ordinary recruiting UI presents one assistant and accepts plain human messages. Its coordinator owns specialist routing, including when pasted text contains agent mentions. System-generated agent identities, addressing controls, tool names, task/artifact IDs and runtime diagnostics belong only in the deployment-owner developer view. Preserve original human-authored messages, useful recruiting evidence, unknowns, clarification inputs and exact external-send confirmations. Product acceptance must start from the ordinary input without `@Main` or specialist-selection instructions; use the existing native handoff mechanism for internal delegation.

Product sign-in and provider authorization are separate. New product users should be able to use platform-configured inference and recruiting services without connecting their own model account. Reuse native deployment configuration and connector authorization; retain the actual caller's user/Space/bot identity throughout. Never achieve shared funding by running customers as the deployment owner, copying an owner's personal OAuth or historical context into new accounts, or giving unrelated customers the same team computer home. Personal conversations, memory, files, caches and routines remain scoped; one person's cross-agent memory is not organization-wide memory. Team sharing must be explicit and authorized. A shared external service credential also requires provider-task ownership enforcement before dispatch, not merely local connection-row isolation or a prompt instruction. Personal mailbox/calendar accounts require their own authorized connection.

New-account recruiting setup is a product capability, not a maintainer checklist: provision the required native agents, recruiting instructions/skills, authorized tools, memory scopes, workspace and routine capability automatically and idempotently from the same maintained product defaults. Fresh approved users must receive the same product functionality without hand-copying prompts or assembling a crew. Do not clone customer history, personal credentials, prior approvals or live scheduled work; repeat sign-in and upgrades must preserve private data and active tasks.

Use the source-workflow review in [PLAN.md — Grok Bot 工作方式的采用与差距](docs/wekruit/PLAN.md#grok-bot-工作方式的采用与差距) when continuing this work. Learn from actual conversations and routine state; an enabled routine or an agent's completion claim is not a verified service outcome. Preserve responsible-agent ownership, useful exception-based updates, scoped and retractable preferences, paid-lookup reuse, and hold/pause decisions. Historical scripts, candidate criteria, schedules and approvals are reference material, not new architecture or permission to replay work.

## Development standard

Every change, by every agent thread, follows this. It adopts maintained industry practice instead of our own: the [Superpowers](https://github.com/obra/superpowers) workflow skills (MIT, vendored unmodified in `.agents/skills/`, loaded through `.claude/skills`) and eval-driven development for agent behaviour. `scripts/check-dev-standard.mjs` checks the machine-checkable parts on every PR. Read [docs/LESSONS.md](docs/LESSONS.md) before starting.

1. **Learn before you build.** Before designing a mechanism, harness or workflow, spend a few minutes on how mature teams and maintained open-source projects already do it, and adopt that (cite it in the plan or PR). Multi-step work starts with `writing-plans` (plans go in `docs/superpowers/plans/`). Bugs follow `systematic-debugging`: root cause before any change; after a second failed fix for the same symptom, stop patching and question the design.
2. **Reuse before you write.** Search for the existing script, helper, tool or harness and extend it. A new test scenario is data in the existing harness, not a new file: live journeys go through the one simulated customer (`infra/acceptance/README.md` says where each kind of test goes), offline agent cases go in `packages/testkit/src/evals/`. Scratch scripts stay out of the repository; a script you need twice becomes an entry point that something calls. Talk to a deployed environment through the shared session client and its live updates, never a polling loop.
3. **Test where it pays, at the cheapest level that catches it.** Tests cost tokens to write, read, run and keep. Write one (red first, per `test-driven-development`) for a real bug's regression, for logic with real branching or state, and for shared mechanisms (auth, sends, approvals, persistence, recovery). Don't write one for glue, copy, config, prompt wording, or anything a journey or eval already covers; never pin instruction sentences in unit tests. Extend an existing test file rather than adding one, and delete a test that no longer protects anything.
4. **Fix agent behaviour with an eval, not a sentence.** When Kruit replies wrongly, reproduce it with the one verification interface and watch it fail: `node infra/acceptance/simulated-customer.mjs --ui --story "<the case in plain words>"` on staging (`--journeys <name>` for a saved one), or an offline case in `packages/testkit/src/evals/`. A recurring complaint becomes a journey in `simulated-journeys.mjs` with its source; it blocks releases only after passing twice. Then fix the mechanism that caused it (the tool result, state, data or guard the agent saw). Change instruction text only when the behaviour really is policy, merge it into the existing rule instead of appending, and name the eval in the PR (`Eval: <journey or case>, <before> → <after>`, linking the run's report). Agent behaviour gets journeys and evals, not unit tests. Three instruction PRs for one scenario means the mechanism is wrong.
5. **Put files where they belong; keep diffs small.** In the repository, code goes in the package and folder that owns its domain (see `docs/CODE-MAP.md` once it lands), never into a giant file: files over 3,000 lines (such as `packages/adapters/src/executor.ts`) take new code as a focused module they call. Change only the lines you mean to; never reformat, reorder or rewrite a file other threads edit. Status reports, handoffs and run logs don't go in the repository; they belong in the PR, the thread, or the project's shared folder under its topic folder (never its root, see the folder's `README.md`).
6. **Evidence before "done".** Follow `verification-before-completion`: no "fixed", "passed" or "done" without the command or staging run that proves it, in this session, and its result. Say "not run" for anything you didn't run; an environment error is "not run", never a pass. A PR's Testing section states exactly what was run, and "done" still means seen working on staging. Before merging to stage, run `pnpm check:standard --base origin/stage --body-file <your PR description>` next to unit-shards, review the diff with `requesting-code-review` (or `/code-review`), and handle comments with `receiving-code-review`.
7. **Record the lesson.** After a miss (a false "done", a reverted fix, a user correction, the same bug twice) add one line to `docs/LESSONS.md`: what happened and the rule that prevents it. A user's decision, such as deleting a file or dropping an approach, stays made: don't restore or rebuild it without asking.

Where a vendored skill says to ask or wait for your human partner, follow this project's rules instead: decide, say what you chose, keep going, and ask only for the irreversible steps listed above. Skill references to subagents, worktrees or skills not vendored here are optional. To skip a check on purpose, write `Standard-Exception: <rule> — <why>` in the PR description; the reviewer sees it. Update the skills by re-copying them from upstream unchanged (`.agents/skills/SUPERPOWERS.md`); project rules live here, not in the skills.

## Repository conventions

- This is a public repository: assume all tracked content and diffs are public. Never commit secrets, `.env` files, private URLs, personal/customer data, or real production data; use fake placeholders. Review `git status` and the staged diff before committing, and never force-add ignored files. If private data appears, stop and alert the maintainer.
- Rakazo is one product across web, Electron desktop, and Expo mobile; Electron hosts the web UI. Put shared behavior, contracts, API logic, and reusable UI in packages. Keep only genuinely native navigation, storage, permissions, and interactions platform-specific. Core workflows must cover every applicable surface or degrade safely for an explicit reason.
- No hosted vendor is required to run the core product. Keep LLMs, sandboxes, memory, voice, integrations, and future external services optional and behind provider-neutral interfaces. Vendor SDKs, configuration, and translation belong only in adapters and composition roots. New providers must reuse shared contracts and deterministic offline conformance tests.
- Keep UI and copy minimal. Show advanced capability progressively and only when it becomes relevant; do not add explainer text that repeats the interface. Frontends express intent and render state; the backend owns orchestration, authorization, validation, retries, recovery, and provider translation. Give controls concise accessible names when needed.
- Treat every visible word as UI. Start UX work by asking what can be removed, and prefer progressive disclosure over persistent explanation or status chrome. If a PR adds user-facing copy, its description must quote the copy, explain why it is necessary, and say why removing it or revealing it only when relevant would not work.
- Configure compatible providers and models through shared connection settings and standard protocol capabilities; never add provider- or model-specific environment variables when the generic connection can express the behavior.
- Use top-level `import type`, never inline type imports. Reserve dynamic `import()` for necessary deferred loading.
- Keep code simple: reuse existing primitives and one source of truth, remove duplication and unused flexibility, and avoid speculative abstractions. Add an interface when it protects a real external or platform boundary, not for its own sake.
- Treat auth, secret handling, sandbox boundaries, host commands, and integrations as security-sensitive. Keep tests deterministic and offline by default.
- The desktop Playwright suite (`pnpm --filter @rakazo/desktop test:e2e`) opens real Electron windows and steals focus on macOS. Do not run it on a maintainer's machine as routine verification; run the unit tests locally and let CI's virtual-display job run the e2e on push.
- Marketing pages (the Astro site in `apps/www`) don't get tests. Check those changes visually and with a build, not with unit or E2E tests.
- Prioritize feature implementation and direct product validation. Run focused checks appropriate to the change; do not wait for CI, CodeQL or review bots after each push. Review available feedback without blocking independent feature work. Use the explicit authorization already recorded in the session for its approved deployment and validation scope; do not ask again for the same scope. PR merging, unapproved production migrations, access expansion and real outbound still require their own authorization.
- PR descriptions say why the change exists, what changed, and how it was tested. Write Why as the product reason (what was wrong and what this changes); never "Elie wants" or a third-person briefing of a named person; the maintainer is the author.
- Commit messages, PR descriptions, issues, and review replies are public too. Describe test results in words instead of pasting tool output, and never include anything that identifies a person, machine, or account: local paths, usernames, hostnames, signing identities, legal entity names, Apple Team IDs, API key IDs, issuer or tenant IDs, account emails, or the accounts, machines, and files that secret values came from. Naming the secrets a workflow reads is fine; use placeholders when a value must be shown.
- For UI changes, link the CI E2E screenshot that shows the change on the PR; add the web test that opens that screen if it is missing. For native-only mobile UI that CI cannot capture, say so in the PR instead of linking an unrelated web screenshot.
- UI system. Colors live in `@rakazo/ui-tokens` as semantic tokens (background, card, muted, border, primary, destructive, ...) with one TypeScript source that generates `tokens.css`; never hardcode a product hex or use `[var(--…)]` arbitrary values. Web and Electron use shadcn/ui on Base UI, vendored into `packages/ui-web` via `pnpm exec shadcn add` from the official registry only (third-party registries are a supply-chain risk); reuse those components before writing chrome by hand, and reuse `apps/web/src/components/ai/` for AI moments (loading, shimmer, success). The app is monochrome: primary is ink, status colors are destructive/success/warning, bots carry the only identity color. Mobile is native-first: Expo Router, Expo UI, native sheets, menus, alerts and pickers wherever one exists; custom surfaces (thread, composer, avatars, cards) use plain StyleSheet with the shared tokens through `apps/mobile/lib/appearance`, and system chrome stays PlatformColor via `lib/native`. Mobile may diverge from web when the native pattern is better.
- On mobile, use built-in native iOS controls (@expo/ui SwiftUI and Liquid Glass, native header items, context menus, alerts, pickers, and switches) wherever possible instead of custom React Native pills or buttons.
